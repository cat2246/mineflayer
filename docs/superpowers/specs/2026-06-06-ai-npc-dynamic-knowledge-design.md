# AI NPC Dynamic Recipe And Blueprint Knowledge Design

## Purpose

The AI NPC should not be limited by hardcoded recipe lists or hardcoded building layouts. The bot should be able to ask for a goal, discover or generate a plan, cache the result, and reuse it later.

This design replaces milestone-era constants such as `SAFE_CRAFT_RECIPES`, `SIMPLE_SHELTER_OFFSETS`, and `LIGHT_AREA_OFFSETS` with a dynamic knowledge layer:

- Mineflayer remains the source of truth for vanilla recipe correctness.
- Codex/AI remains responsible for goals, multi-step plans, and building blueprint design.
- Runtime tools validate and execute plans safely.
- Learned recipes and blueprints are saved to project or per-bot memory.

## Goals

- Let the NPC craft any vanilla item Mineflayer can resolve for the current Minecraft version.
- Let the NPC plan multi-step crafting chains, such as logs to planks to sticks to torches.
- Let the NPC generate and store building blueprints instead of relying on fixed placement offsets.
- Keep execution safe by validating recipes, blocks, locations, radius limits, inventory, and protected blocks at runtime.
- Cache successful plans so the NPC learns over time and does not repeatedly ask Codex for the same simple plan.
- Preserve the missing-tool backlog for unsupported server-specific recipes, custom crafting, or impossible builds.

## Non-Goals

- Do not let Codex directly execute arbitrary code or Mineflayer calls.
- Do not trust AI-generated recipes without Mineflayer validation.
- Do not allow free-form world editing outside a remembered home or explicit future build zone.
- Do not support huge buildings in the first implementation pass.
- Do not solve custom server recipes automatically unless runtime evidence or a human-provided entry exists.

## Core Principle

AI can design and choose. Mineflayer validates recipes. Runtime validates world edits.

## Knowledge Files

Use per-bot memory by default, with optional shared project knowledge later.

Recommended per-bot files:

```text
data/bots/<bot-id>/learned-recipes.json
data/bots/<bot-id>/blueprints.json
data/bots/<bot-id>/build-projects.json
```

Optional shared files for future reuse:

```text
data/knowledge/recipes.json
data/knowledge/blueprints.json
```

Per-bot files should be used first because inventory, home position, server version, and server rules can differ between bots.

## Recipe Knowledge Model

`learned-recipes.json` stores grounded crafting plans, not hardcoded global truth.

Example:

```json
{
  "version": 1,
  "recipes": {
    "torch": {
      "item": "torch",
      "minecraftVersion": "1.21.5",
      "status": "verified",
      "lastVerifiedAt": 1780747200000,
      "plan": [
        {
          "tool": "craft_item",
          "item": "oak_planks",
          "count": 1,
          "requires": ["oak_log"]
        },
        {
          "tool": "craft_item",
          "item": "stick",
          "count": 1,
          "requires": ["oak_planks"]
        },
        {
          "tool": "craft_item",
          "item": "torch",
          "count": 4,
          "requires": ["stick", "coal"]
        }
      ],
      "missingIngredients": []
    }
  }
}
```

The exact schema can evolve, but the important fields are:

- `item`: target item name.
- `minecraftVersion`: recipe version context.
- `status`: `draft`, `verified`, `blocked`, or `failed`.
- `plan`: ordered crafting steps.
- `missingIngredients`: current blockers after validation.
- `lastVerifiedAt`: timestamp for cache refresh.

## Blueprint Knowledge Model

`blueprints.json` stores structured block plans generated by AI and validated by runtime.

Example:

```json
{
  "version": 1,
  "blueprints": {
    "starter-shelter-3x3": {
      "name": "starter-shelter-3x3",
      "status": "draft",
      "size": { "x": 3, "y": 3, "z": 3 },
      "origin": "home",
      "materials": {
        "cobblestone": 20,
        "oak_door": 1,
        "torch": 4
      },
      "steps": [
        {
          "action": "place",
          "block": "cobblestone",
          "offset": { "x": -1, "y": 0, "z": -1 }
        },
        {
          "action": "place",
          "block": "torch",
          "offset": { "x": 0, "y": 1, "z": 0 }
        }
      ]
    }
  }
}
```

Blueprint rules:

- Coordinates are relative offsets, not absolute positions, unless explicitly saved for a current project.
- A blueprint must declare its size and material count.
- A blueprint cannot request protected blocks or destructive edits by default.
- A blueprint starts as `draft` and becomes `verified` only after runtime validation.
- Large blueprints should be split into bounded build projects.

## Build Project Model

`build-projects.json` tracks active or unfinished construction.

Example:

```json
{
  "version": 1,
  "projects": {
    "starter-shelter-2026-06-06": {
      "blueprint": "starter-shelter-3x3",
      "status": "in_progress",
      "originPosition": { "x": 10, "y": 64, "z": 10 },
      "completedSteps": [0, 1, 2],
      "blockedReason": null
    }
  }
}
```

This allows the NPC to stop, resume, and explain unfinished work.

## Tool Design

### Recipe Tools

`inspect_recipe`

- Input: target item and optional count.
- Uses Mineflayer `recipesAll` and item registry to inspect whether the item has a vanilla recipe.
- Does not require ingredients.
- Returns recipe options and whether a crafting table is needed.

`plan_crafting_goal`

- Input: target item and count.
- Uses current inventory, `recipesFor`, `recipesAll`, learned cache, and AI planner context.
- Produces an ordered plan.
- Saves the plan as `draft` or `verified`.

`craft_from_plan`

- Input: saved plan id or target item.
- Validates each step with Mineflayer immediately before crafting.
- Executes steps in order.
- Stops with clear `missing-ingredients`, `missing-crafting-table`, or `missing-recipe`.

`read_recipe_knowledge`

- Reads cached plans and blockers.
- Gives the AI a compact view without flooding the prompt.

### Blueprint Tools

`save_blueprint`

- Input: AI-generated structured blueprint.
- Validates schema, size, material names, step count, and allowed actions.
- Saves as `draft`.

`inspect_blueprints`

- Lists known blueprints, required materials, status, and blockers.

`validate_blueprint`

- Resolves blueprint against home/build-zone position.
- Checks radius, protected blocks, occupied targets, material availability, and max step count.
- Marks blueprint as `verified` when it passes.

`build_from_blueprint`

- Executes a verified blueprint in small batches.
- Records completed steps in `build-projects.json`.
- Stops safely on missing materials, blocked target, or outside-zone errors.

### Low-Level Tools

Keep low-level tools as safe execution primitives:

- `place_block`
- `dig_block`

These should not contain creative layout logic. They only execute one validated edit.

## Replacing Current Hardcoded Constants

Remove or retire:

- `SAFE_CRAFT_RECIPES`
- `SIMPLE_SHELTER_OFFSETS`
- `LIGHT_AREA_OFFSETS`

Replace with:

- Mineflayer recipe lookup for craftability.
- AI-generated crafting plans cached in `learned-recipes.json`.
- AI-generated blueprints cached in `blueprints.json`.
- Runtime validation before each craft/build action.

The runtime may keep small safety allowlists for dangerous actions, such as protected blocks and maximum blueprint size. Safety limits are different from creative content.

## Recipe Flow

1. NPC decides it needs an item.
2. Runtime checks `learned-recipes.json`.
3. If no useful cached plan exists, AI creates a crafting plan.
4. Runtime validates the target item using Mineflayer item registry and recipe APIs.
5. Runtime validates each step against current inventory and available crafting table.
6. If valid, runtime saves or updates the learned recipe plan.
7. Runtime crafts step-by-step.
8. Failures update missing ingredients or missing tools.

## Blueprint Flow

1. NPC decides it wants to improve home.
2. AI generates a small blueprint from the goal.
3. Runtime saves it as a draft blueprint.
4. Runtime validates:
   - size
   - build radius
   - material availability
   - protected blocks
   - target occupancy
   - step count
5. Runtime builds in batches.
6. Each completed step is recorded.
7. If interrupted, the project can resume later.

## Safety Rules

Crafting safety:

- AI-generated recipe steps are advisory only.
- Mineflayer recipe APIs must validate actual recipe availability.
- Crafting table requirements must be respected.
- Multi-step plans must stop when an intermediate item is unavailable.

Building safety:

- Blueprints must be bounded.
- First implementation should cap blueprints at a small size, such as 5x5x4 or 80 steps.
- Building must stay near remembered home or a future explicit build zone.
- Digging must remain more restricted than placement.
- Protected blocks include storage, beds, doors, signs, rails, fluids, bedrock, and other important blocks.
- Runtime should build in batches so the NPC can stop if danger, low food, combat, or user interruption happens.

## AI Prompting

The AI NPC prompt should include:

- Available high-level knowledge tools.
- Compact known recipe/blueprint summaries.
- Current inventory and nearby world state.
- Instruction that AI must save a blueprint or recipe plan before execution when the plan is new.

The prompt should not include full blueprint histories unless needed. Large knowledge stays in files.

## Testing Strategy

Recipe tests:

- Reads and writes `learned-recipes.json`.
- Uses Mineflayer-like fake `recipesFor` and `recipesAll`.
- Rejects an AI recipe when Mineflayer has no matching recipe.
- Plans multi-step crafting from available ingredients.
- Reports missing ingredients clearly.

Blueprint tests:

- Saves a valid AI blueprint.
- Rejects malformed, huge, or unsafe blueprints.
- Validates a blueprint near remembered home.
- Refuses a blueprint outside home radius.
- Executes only a bounded batch of steps.
- Records project progress.

Regression tests:

- `place_block` and `dig_block` remain low-level safe tools.
- The NPC no longer depends on hardcoded shelter or lighting offsets.
- `craft_item` no longer depends on hardcoded recipe names.

## Migration Plan

1. Add recipe and blueprint knowledge storage modules.
2. Add tests for knowledge read/write and validation.
3. Replace `SAFE_CRAFT_RECIPES` with Mineflayer recipe lookup.
4. Add `inspect_recipe`, `plan_crafting_goal`, `craft_from_plan`, and `read_recipe_knowledge`.
5. Add blueprint storage and validation tools.
6. Replace `build_small_shelter`, `light_area`, and `repair_shelter` internals with blueprint-backed behavior.
7. Keep low-level `place_block` and `dig_block` as safe primitives.
8. Update the master SRS milestone notes to reference dynamic knowledge rather than hardcoded recipes and layouts.

## Design Decisions

- Per-bot knowledge should be implemented first. Shared project knowledge should wait until per-bot recipe and blueprint caching is stable.
- Recipe and blueprint source files should be JSON first because runtime validation needs structured data. Human-readable `.md` summaries can be generated later, but they should not be the execution source of truth.
- AI blueprint generation should happen through the existing NPC planner at first. A dedicated planner prompt can be added later if blueprint quality or prompt size becomes a problem.

## Recommended First Implementation Slice

Start with recipe knowledge because Mineflayer gives us strong validation.

First slice:

- Add `learned-recipes.json` path resolution.
- Add `inspect_recipe`.
- Refactor `craft_item` to use Mineflayer recipe data instead of `SAFE_CRAFT_RECIPES`.
- Add `read_recipe_knowledge`.
- Keep blueprint redesign as the next slice.

This removes the most problematic hardcoded crafting limit while keeping the build system safe until blueprint validation is ready.
